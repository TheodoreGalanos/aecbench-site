---
title: Adaptive Harnesses
description: How aec-bench separates the fixed execution kernel, agent-harness configuration, and execution program for governed comparison and repair.
---

Most package users can select an agent harness and use the normal run commands; kernel fingerprints are for governed adaptive experiments. This page is for researchers and maintainers who need governed candidate comparison, replayable repair, or experimental isolation across execution structures.

Adaptive harness experiments separate three objects that are easy to blur together:

- the trusted code that may execute;
- the selected agent-harness configuration; and
- the program that schedules task attempts.

The compact notation is **K / Hx / px**. These identify three library contracts;
learned-harness claims require separate evidence.

## Fixed kernel

The **fixed kernel** (`K`) is the versioned code allowed to execute in an adaptive run. Its identity records the kernel version and a digest of the executable source it owns.

Kernel membership follows executable ownership, independent of a shared checkout. Executable kernel changes produce a new identity, and candidates remain bound to the recorded identity.

## Harness instance

The **Harness instance** (`Hx`) is the content-addressed configuration of the agent
harness used for a candidate. It selects declared agent bindings and their bounded
runtime settings while executable code remains in the fixed kernel.

Typical fields include:

- the agent-harness kind, such as direct, tool loop, RLM, or Lambda-RLM;
- model and endpoint references;
- turn, token, subcall, cost, and concurrency limits;
- declared capabilities and output requirements; and
- the kernel reference against which the instance was validated.

An `Hx` change is therefore an explicit experimental treatment recorded separately
from the incumbent run.

## Execution program

The **execution program** (`px`) is a validated graph of task operations. The fixed kernel compiles it into a `RunBundle` and sends it through the normal aec-bench execution path.

A program can express bounded patterns such as:

- one task attempt;
- independent task fan-out;
- a declared stage graph;
- a coalesced batch operation; or
- a final output-commit step.

Programs contain validated task-operation graphs composed from fixed-kernel primitives.

## K / Hx / px

Keeping the three identities separate makes comparisons interpretable:

```text
fixed K
  + candidate Hx
  + candidate px
  + exact task snapshot
  -> validated RunBundle
  -> Harbor execution
  -> imported TrialRecord and receipts
```

Vary either `Hx` or `px` in one comparison while holding the other and `K` fixed. The
task snapshot, verifier, seeds, repetitions, and shared budget must also remain explicit.

## Compilation and execution

The compiler fails closed before execution when a candidate:

- names a primitive outside the fixed kernel;
- exceeds a declared budget;
- contains an invalid graph or unreachable node;
- refers to an incompatible task or harness profile; or
- cannot bind every execution dependency to the frozen identities.

Successful compilation produces an immutable run bundle. Harbor remains the execution
substrate, and adaptive runs continue through normal task packaging, workspace
isolation, verifier execution, output collection, and trial import.

## Evidence and authority

The host owns acceptance; candidate code may propose a configuration or program.
The host records:

- proposal and compilation identities;
- node and stage receipts;
- task, verifier, and output identities;
- actual budget usage;
- task outcomes and infrastructure failures; and
- the authority decision that allowed any promotion or repair.

Task failure and evidence-system failure remain distinct. Candidate comparison requires
complete receipts, valid imports, and available infrastructure.

## Repair and optimisation

Repair and optimisation are separate uses of the same contracts:

- **repair** starts from a typed failure attributed to `Hx` or `px` and permits only an
  authorised patch to that owner;
- **optimisation** compares a frozen proposal set even when the incumbent is already
  valid.

Claims about learned policies or transfer require separate, preregistered evidence
beyond candidate selection, patching, or comparison.
