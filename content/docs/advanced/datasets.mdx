---
title: Datasets
description: A dataset is a versioned, content-hashed snapshot of a task collection that anchors comparable leaderboard results.
---

Datasets are the formal "this is the benchmark slice" artefact. They sit between task generation and experiment execution, making runs comparable even as templates and tasks continue to evolve.

## Anatomy

A dataset lives under a versioned path:

```text
artefacts/datasets/
└── electrical-v1/
    └── 1.0.0/
        └── manifest.json
```

The manifest pins every included task:

```json
{
  "name": "electrical-v1",
  "version": "1.0.0",
  "content_hash": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "description": {
    "summary": "Electrical engineering benchmark",
    "purpose": "Baseline evaluation for cable and power-system tasks",
    "domains": ["electrical"],
    "difficulty_distribution": { "easy": 3, "medium": 3 },
    "standards": ["AS/NZS 3008"],
    "task_count": 6
  },
  "tasks": [
    {
      "task_id": "electrical/cable-sizing/voltage-drop/example",
      "task_path": "tasks/electrical/cable-sizing/voltage-drop/example",
      "content_hash": "abcdef0123456789abcdef0123456789abcdef0123456789abcdef0123456789",
      "domain": "electrical",
      "difficulty": "easy",
      "tags": ["deterministic"]
    }
  ]
}
```

## Content hashing

Hashes apply at two levels:

1. **Task hash** — SHA-256 over the task directory's sorted file paths and contents, excluding `__pycache__` directories and `.pyc` files.
2. **Dataset hash** — SHA-256 over the sorted `task_id:content_hash` pairs for all included tasks.

`dataset create` writes both fields as exactly 64 lowercase hexadecimal characters.

If a verifier changes, the task hash changes. If a task is added, removed, or changed, the dataset hash changes. Only the sorted `task_id:content_hash` pairs contribute to the dataset content hash.

## Creating a dataset

Freeze existing tasks by domain, difficulty, or pattern:

```bash
uv run aec-bench dataset create \
  --name electrical-v1 \
  --version 1.0.0 \
  --domain electrical \
  --difficulty easy \
  --difficulty medium \
  --summary "Electrical deterministic baseline" \
  --purpose "Comparable cable and power-system evaluation"
```

Freeze the exact output of a generated suite:

```bash
uv run aec-bench generate suite --config suite.toml --output tasks/generated

uv run aec-bench dataset create \
  --name suite-v1 \
  --version 1.0.0 \
  --from-suite-output tasks/generated/dataset.json
```

Use `--overwrite` only when replacing a local mistake before sharing results. Published dataset versions should be immutable.

## Running from a dataset

Validate the recorded task hashes before every dataset-backed run, then generate and run the experiment manifest:

```bash
uv run aec-bench dataset validate electrical-v1@1.0.0

uv run aec-bench dataset config electrical-v1@1.0.0 \
  --model gpt-4.1-mini \
  --harness tool_loop \
  --backend modal \
  --output experiment.yaml

uv run aec-bench run --config experiment.yaml
```

This validation is a separate required gate. `dataset validate` owns live task-hash comparison, while the current `run` selector uses task IDs from a dataset that it can resolve. If the dataset reference is unresolved, the other task filters determine selection.

Manual experiment manifests can also reference a dataset:

```yaml
tasks:
  dataset: electrical-v1@1.0.0
  difficulties: ["medium", "hard"]
```

When the dataset resolves, additional filters intersect with its task IDs.

## Inspecting and moving datasets

```bash
uv run aec-bench dataset list
uv run aec-bench dataset info electrical-v1@1.0.0
uv run aec-bench dataset validate electrical-v1@1.0.0
uv run aec-bench dataset results electrical-v1@1.0.0
uv run aec-bench dataset export electrical-v1@1.0.0 --output electrical-v1.tar.gz
uv run aec-bench dataset import electrical-v1.tar.gz
```

`dataset validate` owns the hash-integrity check and exits non-zero when files are missing or drifted from the recorded hashes. Run it explicitly before `aec-bench run`.

## Versioning policy

Use semver-like discipline:

| Change | Bump |
|--------|------|
| Add tasks while preserving existing task content | minor |
| Change task instructions, verifiers, fixtures, or environment | major |
| Edit non-scoring metadata only | patch |

The practical rule is simple: whenever reward comparability changes, create a new major dataset version.
