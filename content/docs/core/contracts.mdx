## TaskDefinition — what to solve

A `TaskDefinition` is the validated description of one artefact or workspace task. It carries task identity, lifecycle, visibility, instruction, environment, verifier, tools, limits, and metadata.

The task directory supplies the public files:

```text
task/
├── task.toml
├── instruction.md
├── environment/
│   └── Dockerfile
└── tests/
    ├── test.sh
    └── verify.py
```

`TaskDefinition` does not try to model every task output. Task-specific meaning remains with the task and its verifier.

Executable Interactive Worlds use a registered world definition and profile instead of pretending to be a static `TaskDefinition`. Both task families can enter the same experiment, evaluation, evidence, and reporting layers.

### Lifecycle and visibility

Task catalogue status and evidence progression are separate concepts.

| Axis | Values | Meaning |
|------|--------|---------|
| **Task lifecycle** | `proposed`, `active`, `deprecated`, `retired` | Whether a task is ready and supported |
| **Visibility** | `public`, `holdout` | Whether task material can enter public or protected surfaces |
| **Evidence lifecycle** | task-owned checkpoints | Which evidence stage is active during one bounded run |

Visibility is explicit. A missing visibility value is unknown; it is not silently treated as public.

## AgentOutput — what came back

An agent harness returns a minimal `AgentOutput` envelope:

```python
class AgentOutput(StrictModel):
    status: AgentOutputStatus   # completed | partial | failed | empty
    output_path: NonEmptyStr
    output_format: NonEmptyStr
    error_message: str | None = None
```

The harness reports completion and location. Evaluation owns parsing and scoring the task-specific output.

## EvaluationResult — how it scored

`EvaluationResult` owns the normalised reward and the evidence needed to interpret it:

- mechanical validity;
- per-field or task-specific breakdowns;
- error taxonomy;
- confidence metadata;
- attributable human annotations; and
- registered task-specific evaluation extensions.

Invalid or unparseable output cannot receive a positive reward. Reports consume the stored result; they do not recalculate a competing score.

The verifier remains task-owned. It can retain detailed evidence in a task-specific artefact while the shared result carries the normalised outcome.

## TrialRecord — the reportable record

`TrialRecord` is the canonical envelope for one trial. This trimmed view shows the common fields:

```python
class TrialRecord(StrictModel):
    trial_id: NonEmptyStr
    experiment_id: NonEmptyStr
    dataset_id: str | None
    timestamp: datetime
    task: TaskReference
    agent: AgentReference
    environment: EnvironmentSnapshot
    inputs: InputRecord
    outputs: OutputRecord
    evaluation: EvaluationResult
    timing: TimingRecord
    cost: CostRecord | None
    completeness: Completeness      # complete | partial
```

Optional provenance can bind a finite lifecycle, Interactive World episode, or meta-harness study to the same trial.

Both complete and partial records can enter the append-only ledger. A complete record must carry the provenance needed for its execution family. A partial record remains visibly partial; import code must not manufacture missing evidence.

Once accepted, a trial record is immutable. Temporary workspaces and internal builders remain replaceable implementation.

### Output state

`OutputRecord` keeps completion facts separate:

```python
class OutputRecord(StrictModel):
    agent_output: AgentOutput | None
    raw_output_path: str | None
    conversation_path: str | None
    trajectory_path: str | None
    agent_result: dict[str, Any] | None
    artifacts: list[ArtifactReference] | None
    terminated: bool
    truncated: bool
    final_reason: NonEmptyStr | None
```

A result cannot be both terminated and truncated. Provider completion, truncation, and error facts determine execution status independently of reward.

### Artefact integrity

Evidence attached to a trial uses a content-bound reference:

```python
class ArtifactReference(StrictModel):
    kind: NonEmptyStr
    path: NonEmptyStr
    sha256: NonEmptyStr
    media_type: NonEmptyStr
```

The SHA-256 value must match the referenced bytes. A path alone is not evidence integrity.

### Cost tracking

`CostRecord` is the aggregate usage authority. It can record:

- model calls;
- input, output, and cache tokens;
- advisor calls and advisor tokens; and
- estimated cost in USD.

Open-ended provider metadata can retain diagnostics, but reports do not reconstruct aggregate usage from it.

## Trajectory entries

`trajectory.jsonl` is an ordered stream of `TrajectoryEntry` values. Each non-empty line is one validated entry. There is no format header.

Entries can carry the role, content, tool or command details, output, timing, media, and structured metadata for one step. Each object must match the current entry schema.

Provider transcripts remain separate when an external or sealed workflow requires their exact representation.

## Finite lifecycle contracts

`EvidenceLifecycleSpec` declares an ordered set of checkpoints. The task owns instructions, released evidence, submissions, and verification. The host owns the active checkpoint and accepted progression.

Lifecycle run records keep session identity, execution mode, memory visibility, status, usage, and content-bound artefacts. The final trial references that evidence rather than copying it into a second state model.

See [Finite Lifecycles](/docs/core/lifecycles).

## Interactive World contracts

A registered world definition binds an exact executable build and profile to task-owned state, observation, action, transition, and evaluation functions. The episode host adds decisions, recording, limits, termination, and truncation.

A world episode can enter a trial through one verified episode artefact. Shared trial fields do not duplicate task-owned snapshots, transitions, or replay facts.

See [Interactive Worlds](/docs/core/interactive-worlds).

## Design rules

- Validate untrusted, external, persisted, and cross-process data before use.
- Use strict models for repository-owned boundary documents.
- Use lenient models only when an external producer can add fields.
- Keep task-specific payload meaning with the task owner.
- Add a hash only when it protects a named integrity claim.
- Add an ID only for durable identity, correlation, replay, or stale-action detection.
